# TVBoxOS-Mobile fork maintenance rules

- `main` is an upstream mirror. Put all local maintenance changes on `patched`; never commit local patches to `main`.
- Before non-trivial work, reconstruct context from the project Google Drive folder in this order: Entrypoint (Drive Doc ID `1Q7ZvjsDKPpqEa1wfQSy8wcgZBfmEXCaEwZBWiTsgh_c`) -> Master (Drive ID `1wDoQgT9hN8OM4Rf0K2Kv-ZIp439c1m1R`) -> Current Batch pointed to by Master. Master is the sole current execution-authorization authority; the Current Batch is the complete task contract/evidence, not a duplicate authority. Read only relevant decisions listed by the Batch, and Protocol only for governance ambiguity. Do not continue from chat/compaction summaries alone. Legacy ACTIVE-PLAN/FACTS/HANDOFF remain frozen historical references and are not current startup authorities.
- GitHub is the source of truth for code/branches/commits/Actions/releases. Reconcile Drive documents against Git before editing.
- If Master SHA/state disagrees with GitHub on material relevant facts, stop implementation, reconcile the mismatch, and update the docs first.
- For complex work, follow the authorized Current Batch through implementation and validation; do not re-plan settled decisions unless evidence requires it.
- Repository/GitHub implementation writes are allowed only when the current Master Status is exactly `AUTHORIZED` for the Current Batch; `DESIGNING`, `PENDING_ACCEPTANCE`, `NEEDS_REPLAN`, `HUMAN_ACTION_REQUIRED`, and `CLOSED` mean stop without implementation writes. Only the user/main thread authorizes or closes; executors execute only the authorized scope and return `PENDING_ACCEPTANCE`, `NEEDS_REPLAN`, or `HUMAN_ACTION_REQUIRED`. Roles are task-agnostic and never grant automatic authority.
- Follow the authorized Current Batch; a material design, scope, or permission mismatch returns `NEEDS_REPLAN` rather than improvising. Planned human gates return `HUMAN_ACTION_REQUIRED`.
- After each independently verifiable batch: commit to `patched`, run the required build/tests, record verified evidence in the Current Batch/execution log, and leave Master state updates to the user/main thread.
- Documentation semantics: Master = current authorization/state rewrite; Current Batch = living task contract and evidence; DECISIONS = append or supersede; legacy ACTIVE-PLAN/FACTS/HANDOFF stay frozen.
- Never store keystores, passwords, tokens, or other secrets in the repo or normal Drive docs.
- Keep diffs minimal. Do not refactor unrelated code or expand scope without evidence.
- GitHub default branch `patched` is the fork user-facing and normal development/PR base; this does not change D-001: `main` remains the upstream mirror only.
- Upstream maintenance follows `upstream/main -> fork/main -> merge fork/patched`; do not use a direct GitHub Sync fork operation into `patched` as the normal path.
- README cleanup removes human-facing promotion and upstream-personal content only; it never authorizes deleting inherited runtime or resource files.
- U1 automation treats upstream content as unreviewed: candidate validation is read-only and has no signing secrets; only the minimum write job may fast-forward `main`, create a candidate branch, and open a PR.
- U1 never auto-merges `patched`, approves a PR, touches `build.yml`, or enters signing, Environment, tag, Release, or update-metadata paths.
- Autonomous GitHub Actions may execute only the already-authorized workflow contract; an agent's repository write permission does not authorize a workflow to broaden its own trust boundary. U2a's builder has no signing material, the new shared `rc-pipeline.yml` signer is its sole signer Environment consumer, and its verifier/attestor has no signing secrets.
- U1 candidate branches use `automation/upstream-<full-40-char-sha>`; human-facing titles may shorten the SHA, but PR/Issue bodies and markers retain the full upstream identity. Never force-update an existing automation PR, and fail closed on non-fast-forward `main`, unsafe conflicts, or permission errors.
- U1 candidate validation records the full validated Git tree; write/recovery paths must compare the actual candidate branch tree to it before opening a PR. GitHub API pagination/retry/reconcile plumbing stays in the trusted Python helper and uses argv-only subprocess calls.
- U1c watchdog requests enter only through the first read-only `issue_comment:created` gate: the configured fixed Issue must be locked, a normal Issue (not a PR), and the comment actor must be `slashinchi` with an exact Asia/Shanghai production occurrence marker.
- U1c coverage is recorded only after a successful upstream probe by the target repository `GITHUB_TOKEN`; the cross-repository watchdog PAT is Issues-only and must never dispatch workflows or access signing paths.
- F1 release-signing secrets remain Environment-only. During U2a, the new shared RC path exposes them only to the isolated signer job in `rc-pipeline.yml`; candidate validation, ordinary CI, monitor jobs, verifier/attestor jobs and temporary canaries must not access them. The explicitly authorized U2c canary harness may call that same isolated signer only to create a run-owned, non-published canary artifact; it may not publish Releases, move production refs/tags, or write production metadata. All other temporary canaries remain prohibited from accessing signing secrets. The legacy tag publisher remains outside U2a and is removed in the later U2b authority transition.
- F1 canary refs/PRs are disposable shadow state; they must never approve/merge, touch real `main`/`patched`/tags/Releases, or leave a workflow/ref/PR behind. The current planning/authorization role closes Automation Foundation; the execution role returns `PENDING_ACCEPTANCE` or `NEEDS_REPLAN` and never marks it CLOSED itself.
